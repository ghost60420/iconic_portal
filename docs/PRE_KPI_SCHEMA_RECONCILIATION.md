## Safe Correction Plan

1. Keep the current database and pristine copy immutable.
2. Build a new database only from the approved migration graph.
3. Inventory every source table and row count; define explicit source-to-target mappings.
4. Transfer data in dependency order while preserving primary keys and required historical identifiers.
5. For missing employee/profile, permission, notification, and platform rows, run only the reviewed official migration backfills against the candidate database.
6. Resolve the Marketing `0008` name collision by rebuilding the ledger from the approved graph, not by editing or faking the old ledger.
7. Preserve legacy WhatsApp fields in an export until their removal/transfer is proven.
8. Compare row counts, financial totals, identity keys, customer checksums, foreign keys, constraints, and application behavior.
9. Keep the old development database as rollback until the candidate passes every protected regression.
10. Do not replace even the development database until the transfer is reviewed and approved.

No bridge or corrective migration was created because the graph is blocked before a later corrective migration could run. `--fake` is prohibited: schema and history are demonstrably not identical.
