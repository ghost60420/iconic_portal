## A. Root cause

Opportunity **210 / OPP-L1406-001**, The Karma Projects, is linked to **QC-68**, quotation **QQT20260037**, and invoice **69 / INV00057**.

QC-68 is explicitly a sample costing with sample pricing and a quantity of seven. Its CEO approval exists: approved by user 11 at `2026-10-11 06:37:05.472925` UTC. Its quotation was generated by the same CEO at `2026-10-11 06:37:12.670349` UTC, with no quotation revision required. The Quick Costing workflow uses approved costing plus its current generated quotation; it does not have a second independent quotation-approval field.

The production source selector accepted Full Package and CMT pricing but excluded the explicit Sample pricing type. It therefore reported a misleading missing CEO-approved quotation even though approval and quotation existed. Existing production creation also inferred sampling from quantity at most five, incorrectly treating this seven-piece sample as bulk. Separate payment-only readiness messages did not consistently include costing, quotation, and explicit production release approval.

There is also a legitimate payment blocker: invoice 69 totals **CAD 500.00**, has **CAD 0.00 received**, and requires full sample payment. No real payment verification or production exception has been performed. A production release approval is still required even after payment is verified.

## B. Changes made

- Added one production readiness and release gate shared by the existing opportunity, invoice, Quick Costing, and advanced quotation production paths. Every path checks the current source, invoice, payment requirement, actor permissions, and production approval before creating an order.
- Accepted explicit sample costing sources and classified sampling by costing purpose or sample invoice type, including samples with more than five pieces.
- Reused the existing `CRMAuditLog` for production approvals and exceptions. Approval audit persistence is synchronous and transactional: an audit write failure rejects approval.
- Bound approvals to the opportunity, current costing/revision, quotation approval state, invoice identity and commercial terms. Advanced costing line items and SMV are included. Changed terms, recalled/revised costing, and invalid source relationships require a fresh decision. Release re-reads current data so stale invoice objects cannot hide reversed payments.
- Required a separate explicit release action. GET requests to the existing production route open the opportunity readiness section and cannot create orders. Payment verification and production approval do not themselves start production.
- Preserved duplicate prevention, existing production records, locked quotation snapshots, and the established legacy-order linking behavior. Closed/void/archived invoices, missing sources, stale revisions, and mismatched records remain non-waivable blockers.
- Blocked manual production creation/reassignment paths from bypassing the opportunity approval gate, including omitting an opportunity on new manual orders.
- Replaced conflicting opportunity readiness messaging with one section showing costing, quotation, verified payment, required amount, received amount, outstanding balance, production approval, exact blockers, and available authorized actions.
- Reduced redundant opportunity detail reads, including existing linked-record existence checks. Financial formulas and stored historical payment/ledger records are unchanged.

### Why the small new service and partial are necessary

The previous components had separate payment and costing checks but no canonical production release decision shared by all creation paths. `crm/services/production_approval.py` supplies that missing gate and delegates payment requirements to the existing payment helper. It does not post accounting entries or create a parallel payment system. The new partial extends the existing opportunity page and replaces conflicting readiness blocks. Existing URLs, approval endpoints, role permissions, audit storage, invoice fields, and production creation services are reused. No new page, URL, database table, migration, or background job is introduced by this change.

## C. Sampling approval rules

A sample requires approved costing, its current approved quotation, **100% of the invoice total verified**, and explicit production release approval. This rule applies regardless of quantity and cannot be reduced by assigning a bulk deposit percentage to a sample. An authorized user must then select **Move to Production** to create the existing production order. Ordinary employees cannot waive missing requirements.

The gate reads the settled invoice balance maintained by the existing verified-payment posting workflow. A pending employee payment entry contributes nothing to received funds. Existing historical settled balances are preserved; this release does not rewrite historical receipts.

## D. Bulk approval rules

Bulk orders require approved costing, its current approved quotation, the verified deposit specified by that invoice's existing payment terms, and explicit production release approval. No fixed deposit percentage is imposed across bulk orders. Existing positive-payment validation remains in force. Outstanding balances remain visible when the required deposit is satisfied. The existing production workflow begins only after an authorized explicit release.

## E. CEO exception process

An active CEO or Super Admin may select the pending requirements to waive: costing approval, quotation approval, and/or payment. Every exception requires a reason. The same audit row records the approver, timestamp, opportunity ID, waived requirements, and the decision's source/invoice snapshot. The readiness panel shows the exception while continuing to show the actual payment amount and outstanding balance.

A normal costing/production approver retains existing normal approval rights, but receives no CEO exception authority. Finance verification and production release permissions remain separate. The exception does not verify a payment, change an invoice balance, create a payment, or post a journal. It also does not automatically create production: **Move to Production** is a separate POST action.

Changed commercial terms or source revisions invalidate prior approval. An old exception cannot be silently replaced by ordinary approval while its underlying requirements remain unmet. Missing or invalid invoices, mismatched sources, and stale revisions cannot be waived.
